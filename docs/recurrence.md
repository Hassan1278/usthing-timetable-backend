# Recurring events

Daily and weekly series use the existing timed or all-day schedule. The schedule
is the first occurrence and determines its duration. The timetable remains
fixed to Hong Kong; no request can select a timezone.

## Create and store

```json
{
  "title": "Club meeting",
  "eventType": "club",
  "allowConflicts": false,
  "schedule": {
    "kind": "timed",
    "startsAt": "2026-10-05T18:00:00+08:00",
    "endsAt": "2026-10-05T19:00:00+08:00"
  },
  "recurrence": { "frequency": "weekly", "endsOn": "2027-05-31" }
}
```

POST this to `/events` with the existing bearer authorization header. Omitting
recurrence creates a normal event. Omitting recurrence.endsOn resolves it once
to 12 calendar months after the first Hong Kong start date; February 29 clamps
to February 28. Explicit ends must fall between the first start date and that
maximum, inclusive. The end limits occurrence **starts**, not their finishes.
There are no monthly/yearly rules, arbitrary intervals or infinite series.

MongoDB stores one parent with a resolved recurrence and optional embedded
exceptions. Occurrences are calculated, never inserted as separate documents.
A daily series has at most 367 starts, including both endpoints in a leap year.
No new migration is needed for existing normal events without recurrence.

## Read a calendar

`GET /events?from=2026-10-12&to=2026-10-19` returns overlapping normal events and
recurring occurrences, including exceptions moved into that window. Cancelled
instances are absent. Ranges are 1–93 days with exclusive `to`; this bounds one
request, not the series lifetime. Repeated GETs do not write to MongoDB.

An occurrence has the parent's `id`, `uid`, `revision` and recurrence, its
effective fields/schedule, and an `originalStart`. The UI should identify it by
`(id, originalStart)`, never by its moved start or parent ID alone. Timed original
starts are canonical UTC strings; all-day original starts are date-only strings.
A page omits the parent's exception array; GET `/events/:id` returns that array
and the original parent schedule.

Pages still use `limit` (1–100, default 50) and `nextCursor`. Pass the cursor
unchanged as URL-encoded `after`, with the same from/to filters. It may contain
an ID and original start separated by `~`. Ordering is by parent ID and original
start, not by moved schedule time. Pages are live reads, not frozen snapshots.
An ID-only cursor remains supported for normal events. Without from/to,
`GET /events` deliberately lists only non-recurring events across all dates.

## Edit, cancel and restore

All mutations require the current **parent revision** in `If-Match: "1"`.
Successful occurrence operations return 200 with the updated parent and ETag.
A missing precondition returns 428; stale revisions return 412. Unknown/foreign
parents or non-member occurrence identities return 404. Invalid data returns 400.

| Request | Behavior |
| --- | --- |
| `PATCH /events/:id` | Edit the whole series; metadata-only changes preserve the saved end and exceptions |
| `DELETE /events/:id` | Delete parent and embedded exceptions atomically; returns 204 |
| `PATCH /events/:id/occurrences?originalStart=...` | Change one occurrence's fields or schedule |
| `DELETE /events/:id/occurrences?originalStart=...` | Cancel one occurrence |
| `POST /events/:id/occurrences/restore?originalStart=...` | Remove its exception and restore the original occurrence |

URL-encode originalStart, especially `+` in offset timestamps. It must identify
a start actually generated by the parent's rule, including when currently
cancelled. Timed identities require a timestamp; all-day identities require a
date. Re-editing a moved occurrence keeps using its **original** identity.

Occurrence PATCH accepts title, description, location, eventType, schedule and
emailNotifications; supplied nested objects replace their previous overrides.
Other overrides are retained. It cannot change ownership, recurrence, revision
or allowConflicts. Schedule kind must remain the same as the parent. Editing a
cancelled occurrence reactivates it. A moved occurrence may lie beyond the
original series end; its replacement interval is still checked for conflicts.
Overridden fields stay overridden when the parent's metadata changes; other
fields inherit from the current parent.

Changing the parent schedule or recurrence with existing exceptions requires
`clearExceptions: true`. This explicitly removes those exceptions and checks
the resulting full series. `recurrence: null` on parent PATCH converts it to a
normal event at its original schedule; clearing exceptions is required if present.
A supplied recurrence object replaces the rule and resolves an omitted end
against the first start. A schedule-only edit preserves the existing end and
must still satisfy the 12-month bounds. “This and all following” splitting is
not implemented.

## Conflict and resource guarantees

With allowConflicts=false, creates, parent updates, occurrence edits and restores
check **all effective occurrences**, including self-overlap and dates beyond the
93-day reading window. Cancellations remove intervals, and moved overrides replace
original intervals before comparisons. Existing events participate regardless of
their own flag. A candidate with allowConflicts=true explicitly permits overlaps.
Cancellation cannot introduce an overlap and does not need a database conflict scan.

One per-owner lock covers check-and-save for POST, PATCH, DELETE and exception
mutations. Parent revision predicates protect the atomic write. Exceptions are
embedded, so there is no separate exception write that could be orphaned by deletion.
These locks and rate counters are process-local: run **one API process**. Multiple
replicas need database-coordinated writes and shared counters before deployment.
Direct database writes bypass these application guarantees.

Expansion validates rules at runtime, has at most 367 starts per series, and
rejects malformed schedules instead of silently truncating. Multi-series scans
are bounded at 1000 documents and 100,000 generated starts, counting cancellations
too. Database cursors have a 5-second server execution limit and small batches.
Processing-limit errors return 413 before a write or successful partial response.
A narrow range does not necessarily reduce the number of recurring parents scanned;
large calendars may need indexed occurrence envelopes before raising these limits.

Authentication is always checked before these operations. Occurrence dates and
cursors confer no authority: services load the parent using authenticated ownership
and verify occurrence membership. API clients cannot insert their own exception
arrays. Existing IP/read/write request budgets also cover the new endpoints.

## ICS export

Export uses one VEVENT per parent with a finite `RRULE:FREQ=DAILY|WEEKLY;COUNT=n`.
The count includes the first start and is calculated from the inclusive saved end.
Cancelled starts are EXDATEs. Modified occurrences are detached VEVENTs with the
same UID and a RECURRENCE-ID naming the original start. Timed values use UTC;
all-day values use VALUE=DATE. SEQUENCE follows the parent's revision.

A date-range export **selects** parents having an effective occurrence in that
range, but exports each selected series' complete rule and exceptions. It does
not clip a rule or lose moved instances. Unfiltered export includes normal events
and series. Export limits are 1000 scanned documents, 100,000 expanded starts per
processing phase, 5000 VEVENT components, 16 MiB retained document data and 16 MiB
output. Oversized exports fail with 413 rather than produce a partial calendar.
Fractional seconds round outwards, as in normal-event export. Export is a snapshot,
not synchronization, and includes no account IDs, tokens or notification alarms.

ICS semantics follow [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545).
Integration tests parse the generated ICS with ical.js, expand its rules and
exceptions, and compare resulting times to calendar API responses.
